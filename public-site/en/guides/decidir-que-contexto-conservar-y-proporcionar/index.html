Deciding what context to preserve and when to provide it

Criteria for separating durable knowledge from task procedures and choosing how much context an agent needs.

The decision

Section titled “The decision”

When preparing an agent to modify a service, decide which information should stay versioned with the system, which procedure should be retrieved for the task and which checks must precede an action. This guide proposes criteria for a fictional architecture; it describes neither a tested implementation nor professional experience.

Example context

Section titled “Example context”

Imagine a billing service at a fictional company. An agent receives a task to change retry handling. The team has a repository with tests and CI, a diagnostic procedure and a tool querying metrics. No specific technology, access to real data or execution results are assumed.

Alternatives and tradeoffs

Section titled “Alternatives and tradeoffs”
Approach When it fits Cost or risk
Keep existing repository artefacts A small, familiar service whose tests and contracts express necessary constraints Operational procedures or decision reasons may remain hard to find.
Version specifications, tests and architecture checks Frequent changes, several maintainers or costly constraint violations Artefacts need review and must avoid duplicating or contradicting code.
Provide procedures and tools on demand Tasks vary by service and maintained instructions or external signals exist Procedures become stale; tools need clear permissions and boundaries.
Combine versioned knowledge and task retrieval The agent must respect durable contracts and follow specific operational steps Integration and maintenance responsibilities may outweigh value for a simple task.

If a test and contract already cover the need, an additional context platform may add little. Start with the simplest solution that makes intent discoverable, supplies necessary procedures and checks the outcome.

Selection criteria

Section titled “Selection criteria”
  1. Separate stable knowledge from task context. Behaviour rules, acceptance criteria and architecture boundaries belong in artefacts versioned with the system. Steps varying by alert, service or change can be retrieved as task procedures.
  2. Find a source of truth. Before copying information elsewhere, identify who can change it and which artefact is current. References should lead back to it.
  3. Consider the cost of error. Changes affecting data, money, security or availability need relevant tests and automated limits. Textual guidance is not implicit permission to act.
  4. Limit tools to the task. Grant minimum necessary access. Separate reading from writing and require approval for external or hard to reverse effects.
  5. Assign maintenance. Each specification, control and playbook needs an owner and a signal triggering review when the system changes.

Walkthrough

Section titled “Walkthrough”

For the fictional billing service, the agent would retrieve the retry change procedure and consult metrics only if diagnosis is required. Before proposing code, it should locate expected behaviour and its test. If absent, it would stop automatic implementation and ask the team to define and review the criterion first, rather than infer it from conversations or isolated examples.

After a proposed change, CI would run tests and relevant architecture controls. The agent would present consulted artefacts, checks performed and checks it could not complete. A person would review correctness and approve operational actions. This walkthrough is illustrative and has not been implemented or executed.

Checking whether the decision helps

Section titled “Checking whether the decision helps”
  • Check whether the agent identified each specification and procedure and their versions.
  • Record passed and failed checks, human corrections and later regressions.
  • Assess whether retrieval saves steps without increasing incorrect actions or unnecessary permissions.
  • When stale information is found, assign correction and identify dependent artefacts.
  • Compare similar tasks using predefined correctness criteria; generation speed alone is insufficient.

Signals to simplify or redesign include unused playbooks, duplicate rules, discrepancies between documentation and tests, broad permissions and green checks that miss relevant failures.

Limits and references

Section titled “Limits and references”

These criteria draw on Berhe, Bragner, Maran and Jayaraman’s Context Store article and Ajay Prakash’s LinkedIn playbook and MCP presentation. Their combination and the example are editorial work; the sources do not evaluate this workflow. It is a decision guide, without executable tutorial steps or tested results. The related synthesis distinguishes source evidence and open questions.
