Agentic architecture: context, coordination and boundaries

An introduction to architectural decisions for adding agents to existing systems.

The central idea

Section titled “The central idea”

What changes in an architecture when we add agents? Rafał Gancarz argues that agentic architecture extends existing systems with agents working with context, knowledge and tools. His thesis is that these capabilities will coexist for years with microservices and cloud-native architectures, which will continue to provide much of the necessary infrastructure.

The expectation that this architecture will dominate the industry is the author’s forecast, rather than an established conclusion. His immediate practical argument is that agents change decisions about context, coordination, security and operations.

From data to knowledge

Section titled “From data to knowledge”

Traditional systems incorporate rules and process information through application logic. Gancarz observes that people also contribute procedures, shared knowledge and judgement in many processes. Agents allow some of that knowledge to participate in execution, although their outputs require appropriate handling and checking.

This adds a probabilistic dimension. The same objective can lead to different decisions or tool calls; alongside service design, we must decide what information the agent receives and how its actions are inspected.

An architecture with another layer

Section titled “An architecture with another layer”

Imagine an application with APIs, services and databases. Adding an agent gives it another way to use those components for a task. Someone must decide how the goal arrives, which information it can consult, which actions are permitted and how the result is returned.

This is a simplified editorial diagram. An implementation may contain several agents, queues and validation steps; the point is that behaviour depends on the surrounding system’s interfaces and constraints.

Context and memory

Section titled “Context and memory”

The article describes a shift from fixed instructions towards dynamic context, including other agents’ outputs or information retrieved through RAG. Progressive disclosure supplies details when needed rather than putting everything in every request. Context management selects, stores and reuses useful information within the model’s effective limits.

Memory adds another dimension. The author distinguishes episodic memory for past experiences and decisions, semantic memory for facts and definitions, and procedural memory for rules and behaviours.

Memory Question it helps answer
Episodic What happened in a previous situation?
Semantic What facts or concepts do I know?
Procedural Which steps or rules should I follow?

These categories organise retrievable information; storing an experience does not guarantee correct selection or interpretation.

Why not send all the documentation?

Section titled “Why not send all the documentation?”

More information is not always helpful: it occupies space and can make relevant details harder to find. Progressive disclosure asks: what does the agent need for this step? It can start with general guidance and retrieve more specific procedures or data later. Retrieval itself needs selection criteria and controls over what reaches the model.

Memory is not a single magical notebook. An experience can recall what happened, a current rule can guide a decision and a procedure can explain how to perform a task. Usefulness depends on freshness and retrieval at the right time.

Integration and domain boundaries

Section titled “Integration and domain boundaries”

Gancarz describes agents inside API services, as MCP tools or through A2A communication, and as asynchronous message consumers. MCP connects agents with external tools and sources; A2A seeks to facilitate communication between agents.

The article proposes keeping interactions within bounded contexts from domain-driven design. Restricting tools and data to the relevant scope can reduce dependencies and the impact of changes. In a fictional editorial example, an order agent would use authorised order services and reach other domains through agreed interfaces rather than unrestricted database access.

The interface represents defined access between domains; specific permissions depend on the task.

Why do boundaries matter?

Section titled “Why do boundaries matter?”

Suppose the order agent needs shipment status. An agreed interface can provide it without unrestricted access to another domain’s data. Each team can maintain its part with fewer direct dependencies. Authorisation, contracts and failure handling still need to be defined.

MCP and A2A connect components, but a shared protocol does not automatically determine who may do what or resolve responsibility across domains.

Coordination and performance

Section titled “Coordination and performance”

More agents do not automatically mean better results. The author cites Google and MIT research comparing strategies and concluding that suitable coordination depends on the task, using financial reasoning and web navigation as examples with different needs. This does not establish those choices as optimal for every system in those domains.

Alongside latency, throughput and errors, Gancarz proposes measuring quality and spend. Experimentation should consider representative tasks, model calls, communication and response requirements.

Centralised coordination can support a shared view; distributed coordination can allow parallel exploration. Each adds exchanges and possible failure points, so compare actual quality gains with additional time, cost and complexity.

Security and observability

Section titled “Security and observability”

The article identifies prompt injection, manipulated tool outputs and exposure of data to model providers. It also discusses capability-scoped permissions and task-scoped credentials. Authorisation needs enforcement in the tools and services executing actions, alongside instructions guiding the agent.

The author recommends structured logs with correlation and protection of personal information, task and tool traces, quality, latency and cost metrics, alerts and runbooks. These signals support investigation but do not replace quality evaluation.

A practical question makes this concrete: if an answer is wrong, can we establish what context the agent received, which tool it used and what result it obtained? Traceability should avoid collecting unnecessary personal data.

Platforms and scope

Section titled “Platforms and scope”

Gancarz expects memory, registries, controls, orchestration and observability to become common platform capabilities. He also recognises that some processes do not need agents or justify their cost. These are considerations to assess rather than adoption or savings guarantees.

My reading

Section titled “My reading”

The useful contribution is treating the agent as part of a system with boundaries and responsibilities. Before selecting a platform or multiplying agents, clarify which task needs probabilistic judgement, which tools it requires and how its outcome will be measured. The cited strategy comparison encourages experimentation rather than a universal recipe.
