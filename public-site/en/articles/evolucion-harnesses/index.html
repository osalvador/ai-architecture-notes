From chains to graphs and code: choosing the agent environment

Three ways to structure agent execution and their complexity tradeoffs.

Agent design

Original sources

  • The Evolution of Agentic Harnesses: from Chains to Graph to Code ↗ · Karthik RamgopalArticle · English

The central idea

Section titled “The central idea”

A simple chain, a graph, or an agent that writes code? Karthik Ramgopal describes chains, graphs and code harnesses as three ways to organise execution around a model. Each provides different control and recovery capabilities, with different design and operating costs.

Approach How it progresses Where it may fit
Chain Sequential steps A narrow, predictable task.
Graph Explicit routes and state A task with decisions and retries.
Code Generate, execute and check A solution verifiable through tools.

These are design options; the choice depends on required guarantees, cost and latency.

First: what does the harness do?

Section titled “First: what does the harness do?”

The model generates probabilistic outputs. The harness organises the surrounding work: preparing inputs, calling the model and tools, maintaining state and collecting results. Depending on its design, it also validates, retries or requests human intervention.

The article describes three approaches drawing on the author’s experience. They are not mandatory maturity levels: a chain can remain the best option when it delivers adequate quality.

Chains: a simple sequence

Section titled “Chains: a simple sequence”

A chain connects steps in order. Like a small assembly line, each step receives what the previous one produced. LinkedIn’s example uses routing, retrieval and generation. It is quick to build and may suffice for narrow tasks, but an early error can propagate if it goes undetected. A simple flow still needs evaluation.

If routing misclassifies the question, later steps may use the wrong information. Reviewing classification can reduce that risk, while adding work and cost. The key is identifying which errors matter for the specific task.

Graphs: explicit control

Section titled “Graphs: explicit control”

Graphs represent tasks as nodes and transitions as connections. They express branching, retries, validation and state. The author describes their use for long running work and human involvement. As cases and recovery paths multiply, the graph itself can become difficult to maintain.

Code: execution and feedback

Section titled “Code: execution and feedback”

In a code harness, the agent can generate a solution, run it in isolation, observe errors and revise it. The article identifies isolation, logging, validation and an iterative refinement loop as important components. Its example generates queries and code to analyse data under access and governance controls.

Running a program or passing a test does not by itself prove that it solves the problem: the guarantee depends on the checks and environment. The author presents experience and design criteria, rather than a universal comparison of implementations.

This editorial diagram shows validation against defined criteria. When a failure is detected, the agent can revise the proposal and try again.

What does a check actually guarantee?

Section titled “What does a check actually guarantee?”

Code can run and return a repeatable result under given conditions while solving the wrong problem. A test covers only what has been expressed in it; data, permissions and external effects matter too. Isolation and validation reduce specific risks without automatically making every output correct.

In Ramgopal’s example, the agent produces SQL and Python for analytical questions, tests its solution on sample data and applies checks before continuing. It illustrates feedback guiding iteration, rather than demonstrating that every similar system has the same safety or quality.

Choosing for the task

Section titled “Choosing for the task”

The article recommends the least complex solution that meets reliability, latency and cost needs. A chain may suffice for a summary; a graph expresses explicit routes; code execution helps when tools can check and refine the result. Separating planning from execution, validating model outputs and observing the flow remain relevant across all three.

Three questions provide a starting point:

  1. Are the steps known and few? A chain may suffice.
  2. Do we need explicit routes, state and decision points? A graph may make them easier to inspect.
  3. Must the task construct and check an executable solution? A code environment may provide a test and correction loop.

In each case, measure whether the result meets the actual need. More model calls or retries may improve some cases while increasing latency and spend.

My reading

Section titled “My reading”

The progression is useful as a map of alternatives, rather than an obligation to migrate towards code. Start with the guarantees the task needs and how to measure them, then decide whether the extra complexity is justified.
