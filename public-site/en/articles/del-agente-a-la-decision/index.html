The idea in one sentence

Section titled “The idea in one sentence”

Reading and modifying code is only part of an agent’s competence in a mature organisation. It also needs to know which tools exist, how common tasks are performed and where knowledge outside the repository lives.

In Context Engineering at LinkedIn, Ajay Prakash describes a layer of tools and playbooks consulted through MCP. It supplies procedures and organisational context when the task requires them, rather than making every engineer explain them again.

Code does not contain all the context

Section titled “Code does not contain all the context”

Prakash starts from early coding agent experiences. Agent mode could edit files and run commands, but results were unreliable across many repositories, services, frameworks and infrastructure. Engineers had to guide the agent continuously and supply missing details.

Connecting existing code search, documentation and other tools helped locate information absent from the model. For more complex tasks, retrieving fragments still fell short:

Hard to discover details included dependency installation, build and test commands, steps for investigating alerts, and local practices accumulated in wikis, conversations and experience.

Playbooks: memory for how to do something

Section titled “Playbooks: memory for how to do something”

LinkedIn treats playbooks as procedural memory. A playbook has a name, description and task instructions. Its description helps the agent select it; invocation returns steps and context.

For an Airflow pipeline request, for example, the agent can obtain LinkedIn’s procedure and conventions alongside the person’s requirements. Teams contribute and share playbooks through a central repository.

Prakash highlights two principles:

  1. Bounded purpose: each playbook addresses a recognisable task and is sufficiently self-contained. Split procedures covering unrelated tasks.
  2. Composition and progressive disclosure: a broader playbook may refer to smaller ones, loaded when needed rather than all at once.

This keeps a large catalogue available without loading every instruction into each interaction. Playbooks form a traversable network with common and repository-specific instructions.

Tools, playbooks and access

Section titled “Tools, playbooks and access”

MCP lets agents discover and invoke tools. A local MCP server exposes central and local tools and playbooks. Tools can search code and documentation or consult other systems. They require authentication and, according to the speaker, information security review.

Showing thousands of tools directly occupied excessive context and hurt performance. LinkedIn introduced staged access:

This lets an agent request appropriate tools for a task instead of loading the full inventory initially, addressing the context overload described in the talk.

The incident example

Section titled “The incident example”

Prakash describes an on-call engineer giving an agent a latency alert link. The agent consults diagnostic instructions, retrieves service logs and metrics, follows a dependency and finds a recent change that might explain errors. It prepares findings and possible mitigation. The speaker says the person confirms and verifies before mitigation is executed; the agent may then prepare a report and pull request.

The value includes knowing which tool to consult, in which order and with which procedure to reach a verifiable hypothesis.

Maintenance is part of the design

Section titled “Maintenance is part of the design”

Procedures become stale as systems change. Prakash explains that playbooks can be updated from session discoveries, while identifying updating as still manual: someone must remember or ask for new learning to be incorporated.

LinkedIn was exploring automatic discovery of frequent workflows and gaps from pull requests, sessions and telemetry. This was future work, rather than an already delivered and validated capability. Ownership is explicit: the central team maintains shared infrastructure; contributing teams maintain their tools and playbooks; unused or unmaintained entries can be retired.

This raises operational questions: who keeps instructions current, who can add tools and which actions need review? The talk describes tool security review and quality and reliability guardrails from the outset.

What the presentation supports

Section titled “What the presentation supports”

Prakash argues that simply giving teams agents is insufficient in a large organisation. Agents need practical access to procedures and context, alongside quality controls and a usable developer experience.

InfoQ’s summary reports 20% productivity gains without reduced reliability. The transcript does not explain method, period, sample or baseline. Attribute that figure to the presentation or its description; it is not a transferable guarantee.

The talk reports LinkedIn’s large scale experience rather than evaluating smaller organisations or comparing playbooks with alternatives. This summary uses the transcript and description; video and slides were not reviewed.

Connection with Context Store

Section titled “Connection with Context Store”

Context Store preserves intent, tests and architectural constraints alongside a system. LinkedIn focuses on procedures retrieved when starting a task.

Combining them is an editorial proposal, not an integration described or evaluated by Prakash. The pilot synthesis explores complementarity and limits; the guide applies criteria to a fictional service.

My reading

Section titled “My reading”

The useful part is converting tacit knowledge into retrievable, reusable procedures without putting everything in the initial prompt. Separating search, discovery, inspection and invocation recognises that a large catalogue becomes noise when shown all at once.

Having a playbook does not establish its correctness. Stale instructions can accelerate a wrong action. I would start with consultation and diagnosis procedures, source references and clear owners, expanding actions with checks and human approval appropriate to their impact.

The question I retain is: what must the agent know before starting, what can it discover along the way and what must it demonstrate before acting? It connects procedures with specifications, tests and boundaries without conflating them.
